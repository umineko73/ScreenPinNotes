# 定期コードレビュー

## 呼び出し方

このリポジトリを開いたエージェントに、次の指示を渡す。

```text
docs/periodic-review.md に従って定期レビューを実施してください。
前回のレポートと現在のコードを比較し、保守性・構造・性能・不具合予防の観点から
根拠付きのリファクタリング案を優先順位順にまとめてください。
実装は変更せず、結果を docs/reviews/ に保存してください。
```

推奨頻度は月1回と、大きな機能追加・リリースの前。変更が多い時期は週1回にする。
この文書は再利用するタスクの定義であり、自動実行のスケジュールを登録するものではない。

## 目的と作業範囲

- 変更の影響を限定し、データを守り、検証しやすい構造へ改善する。
- レビューと提案を行い、成果物はレビューのMarkdownレポートとする。
- 実装・設定・テストの修正、依存更新、コミット、外部への投稿は含めない。
- 作業中の変更を保持する。現在の作業ツリーを対象とし、未コミット変更の有無を記録する。
- 行数やクラス数だけを理由に分割を提案しない。具体的な影響、変更理由、改善効果を示す。
- 過去の指摘は現在のコードで再確認する。解消済みの指摘を繰り返さない。

## 手順

1. リポジトリの作業指示、`CLAUDE.md`、`docs/note-state-and-persistence.md` を確認する。
2. 日時、ブランチ、HEAD、`git status --short` を記録する。
3. `docs/reviews/` の直近レポートを読み、記録されたHEADが利用可能なら差分を確認する。
   未コミット変更と未追跡のソースも確認する。履歴がない場合は比較不能と明記する。
4. 差分とその呼び出し元・呼び出し先を重点的に読み、下記観点で横断的に確認する。
   前回から実装変更がない場合は、その事実と未解決事項を簡潔に報告する。
5. 前回指摘を「未解決・改善中・解消・再評価」に分類し、根拠を添える。
6. 変更内容と疑わしい経路に対応する既存テストを実行する。
   月次の全体レビューまたは初回レビューでは、Windows/.NET環境で次を実行する。

   ```powershell
   dotnet test tests/ScreenPinNotes.Tests/ScreenPinNotes.Tests.csproj --verbosity minimal
   ```

   実行コマンド、成功・失敗・スキップ件数、警告、未検証範囲を記録する。
   実行できなければ理由を明記し、過去の結果を今回の結果として扱わない。
   アプリや手動検証を起動する場合は、一時データ保存先を使い、実データを変更しない。
7. 優先度付きの提案と、次に取り組む小さな変更をレポートにまとめる。
8. `docs/reviews/YYYY-MM-DD.md` に保存する。同日分があれば上書きせず時刻を付ける。
   最後に差分を確認し、レポート以外の意図しない変更がないことを確かめる。

## レビュー観点

| 観点 | 確認する内容 |
| --- | --- |
| 責務と依存 | App/Windowへの処理集中、partial間の共有状態、App.Current依存、重複した業務ルール |
| 状態遷移 | 編集・閲覧・折りたたみ・アニメーションの整合性、イベント抑止、再入、終了後のコールバック |
| 永続化 | 変更対象だけの保存、保存順序、失敗後の再試行、終了時の確定、削除後の再保存、読み込み失敗の扱い |
| 性能 | UIスレッドのI/O、全件処理、全文再描画、通知の集約、画像キャッシュの寿命、監視・タイマーの解放 |
| 並行処理 | 古い結果の反映、キャンセル、共有状態へのアクセス、監視解除と通知の競合 |
| テスト容易性 | privateへのリフレクション依存、実時間待ち、共有グローバル状態、純粋なロジックの分離 |
| 表示と互換性 | Markdownの元テキスト位置、Undo、外部ファイルのキャッシュ、DPIとモニタ構成、既存保存形式 |

維持すべき仕様：保存処理が未登録の付箋フォルダを削除しないこと、削除済み付箋を
保存待ち処理で復活させないこと、外部ファイル読み込み失敗時に本文キャッシュを壊さないこと、
一時的な画面配置を本来の保存位置へ混入させないこと。

## 指摘の書き方

重要度は「高＝データ保全・操作停止・広範囲な不具合のリスク」「中＝変更容易性や検証性の改善」
「低＝局所的な整理」とする。確定した不具合、コードから分かる設計上のリスク、未計測の性能仮説を区別する。
指摘数を埋めるための提案はしない。

各指摘に以下を含める。

- 継続追跡できるID（初回は R001 から）、重要度、前回からの状態
- 対象ファイルと行番号、具体的な処理経路
- 問題が現れる条件と利用者・開発への影響
- 最小限の改善案、期待する効果
- 移行リスク、維持する仕様、確認する既存テストや不足する検証

性能を測定する場合は、付箋数・本文量・外部ファイルサイズ・環境をそろえ、
保存回数、操作待ち時間、メモリ使用量などを比較する。未計測の値を推測で記入しない。

## レポートの構成

1. 対象日時・HEAD・ブランチ・未コミット変更・比較元・確認範囲
2. 全体評価と前回からの変化
3. 優先度順の指摘（根拠、改善案、移行リスク、検証方法）
4. 前回指摘の追跡表
5. テスト結果・計測結果・未検証事項
6. 次に実施する変更案（独立してレビューできる規模で1〜3件）
