# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
dotnet build                     # build (Debug)
dotnet build -c Release          # build Release
dotnet run --project src         # run the app locally
dotnet test                      # run tests/ScreenPinNotes.Tests
```

`tests/ScreenPinNotes.Tests` uses xUnit v2 and `Xunit.StaFact` 1.2.69. `TestHostDpiAwareness` opts the test host into PerMonitorV2 (testhost.exe does not use the app's manifest, and without it `GetDpiForMonitor` reports every monitor at the process scale, so mixed-DPI monitors are invisible); placement tests that need a monitor at another scale return early on uniformly scaled machines. Use `[WpfFact]` / `[WpfTheory]` for WPF controls, focus, native window ordering, and hotkey registration. The suite covers services, models, reminder dialogs, settings layout, new-note input focus, and note-list sorting. WPF tests share `WpfApplicationFixture` and run without parallelization. Use a temporary `StorageService` root and restore shared app state in cleanup. Native ordering tests inspect real window handles; drag/resize behavior still benefits from manual verification.

To avoid touching your real notes while testing, point the app at a scratch data folder:

```bash
SCREENPINNOTES_DATA=/path/to/scratch dotnet run --project src
```

Build release zips (self-contained + framework-dependent) into `artifacts/`:

```bash
powershell -ExecutionPolicy Bypass -File scripts/publish.ps1            # uses <Version> from the csproj
powershell -ExecutionPolicy Bypass -File scripts/publish.ps1 -Version 0.2.0
```

Releases are also built by CI: pushing a `v*` tag triggers `.github/workflows/release.yml`, which runs the same `publish.ps1` and attaches both zips to a **draft** GitHub release — publish it manually afterward. Because `publish.ps1` names the zips from the csproj `<Version>` rather than the tag, that workflow first fails the run unless the tag equals `v` + `<Version>`; bump the csproj, commit it, then tag that commit.

## Architecture

Single WPF project targeting `net8.0-windows` (`src/ScreenPinNotes.csproj`, `OutputType=WinExe`). No MVVM framework, no DI container — plain code wiring throughout.

**Single-instance app, one `Window` per note.** `App.xaml.cs` is the entry point: it owns `AppSettings`, the list of open `StickyNoteWindow`s, and the tray icon (`System.Windows.Forms.NotifyIcon`, mixed into the WPF app). A second launch is prevented via a named `Mutex` keyed off the resolved data root, and a registered Windows broadcast message asks the already-running instance to show all notes before the newcomer exits — see the "二重起動防止" block in `App.xaml.cs`.

**Notes are files, not a database.** `StorageService` persists everything under `%APPDATA%\ScreenPinNotes\` (overridable via the `SCREENPINNOTES_DATA` env var): `settings.json` for `AppSettings`, and one `notes\{id}\` folder per note holding `meta.json` (everything on `StickyNote` except `Content`, which is `[JsonIgnore]`), `content.md`, and an `assets\` folder for pasted images. Keeping the Markdown body in its own file (instead of JSON-embedded) keeps notes human-readable/diffable. Writes are atomic (write `.tmp`, then `File.Move` with overwrite) and debounced per `AppSettings.Timings.SaveDebounceMs` (800ms default). `StorageService.Save` never deletes folders that aren't in the in-memory list — only explicit `DeleteNote` does — because two instances sharing a data folder previously caused one to erase the other's notes; keep that invariant if you touch save/load. Only the current per-note folder format is loaded; legacy app folders, environment variables, and single-file note data are not migrated. The instance persistence methods (`Load`/`Save`/`SaveNote`/`DeleteNote`/`LoadSettings`/`SaveSettings`/`GetNoteDirectoryPath`/`GetNoteAssetsDirectoryPath`) resolve paths from an instance root that defaults to the static `DataRoot`/env-var resolution; pass a temp directory to `new StorageService(dataRoot)` to get an isolated instance in tests. `App.xaml.cs` builds one `StorageService` and threads it through `SampleNoteFactory.CreateInitialNotes` and every `StickyNoteWindow` constructor, so note/asset path resolution (`GetNoteDirectoryPath`/`GetNoteAssetsDirectoryPath`) always goes through that shared instance rather than a static helper — this is what lets tests construct their own `StorageService(tempDir)` without touching real user data. Note IDs are validated (`IsSafeNoteId`) before being turned into a path, rejecting anything that could escape the notes folder (e.g. a corrupted `Id` containing `..`). The remaining *static* members (`DataRoot`, `SettingsPath`) stay static because `App.xaml.cs` needs `DataRoot` for the single-instance mutex key before any `StorageService` instance exists.

**Window chrome is largely code-behind, not the ViewModel — split across partial-class files by responsibility.** `StickyNoteWindow` (`src/Views/`) is one class split across `StickyNoteWindow.xaml.cs` (fields, constructor, settings/localization application, window lifecycle, autosave — the "core" file) plus `.Content.cs` (Markdown/plaintext loading, images, hyperlinks), `.EditMode.cs` (edit/view mode switch, status bar grow/shrink, focus handling), `.Clipboard.cs` (paste, Excel table paste/copy via `MarkdownTableClipboard`, pasted images, files pasted or dropped and copied into `assets` via `ImageAssetImport`), `.FileChips.cs` (files placed on a note: Explorer icon, click to open), `.ContextMenus.cs` (title/content right-click menus, opacity, z-order), `.WindowChrome.cs` (drag, snap, `WM_SIZING` resize hook, DWM appearance suppression, `WndProc`), `.Fold.cs` (fold/unfold + animation), `.Toolbar.cs` (title-bar buttons, size overlay), and `.Popups.cs` (color/icon/font pickers), `.Monitors.cs` (monitor-layout aware placement), and `.Reminder.cs` (a non-interactive animated reminder border). This is a purely mechanical split along section-divider comments the original single ~2300-line file already had — no behavior change, and every file still shares the same private fields freely since C# partial classes don't restrict that. `ViewModels/StickyNoteViewModel.cs` is thin by comparison — mainly theme-aware brush/color derivation (light/dark, per-note color key, opacity) — so don't expect note-window logic to live in the ViewModel by default. Each note window is `WindowStyle="None"` + `WindowChrome` for the custom title bar, and `AllowsTransparency="True"` for per-note semi-transparency (`StickyNote.OpacityPercent`, boosted on hover via `AppSettings.HoverOpacityBoostPercent`). `AllowsTransparency` was previously avoided by design (risk of breaking `WindowChrome` resize hit-testing) before shipping this way — if you touch `.WindowChrome.cs`, verify resizing/dragging still works by actually running the app (with a real mouse — synthetic/scripted clicks were not reliably observed reaching this app's windows when tried), since that regression risk was never fully re-verified and none of this file's code is unit-testable.

**Markdown is hand-rolled, not a library.** `Services/MarkdownRenderer.cs` parses a Markdown subset (headings, bold/italic, inline code, fences, lists/checkboxes, blockquote, hr, tables, images, links) directly into WPF `FlowDocument` `Block`s — no Markdig or other dependency. Edit mode always shows/edits the raw source string; only View mode renders through `MarkdownRenderer`, so content is never mutated by the renderer. Lists nest by indentation (2+ columns; a tab is 4) and ordered lists keep their start number; consecutive `>` lines become one `Section` whose stripped content is rendered recursively, so `>>` nests. Both nest at most `MaxNestingDepth` levels. Each rendered line carries its original line index and column offset (`SourceLine`) because task checkboxes and image resizing rewrite the source by position. `MarkdownIndentation` implements the editor's Tab / Shift+Tab line indenting and Enter list continuation. `==text==` highlights (not when the inner text starts or ends with whitespace). `AppSettings.JoinMarkdownLines` (off by default, so line-per-line memos keep their look) wraps consecutive plain lines into one paragraph until a blank line, another block, or an indent change.

**Localization is `.resx` catalogues.** `Services/LocalizationService.T(key)` looks the key up in `Resources/Strings.resx` (English) and `Resources/Strings.ja.resx` via a `ResourceManager`, falling back to English and then to the key itself. Adding UI text means adding a `<data name="...">` entry to **both** files — a missing key silently renders as the key name, so cover new strings with a test that asserts the actual text. See `docs/localization.md`.

**Sample notes are real files, copied at first run.** `SampleNoteFactory` reads `meta.json` + `content.md` per language/kind from `SampleNotes\{ja|en}\{markdown|usage}\`, which the csproj copies next to the built exe (`CopyToOutputDirectory=PreserveNewest`). On first launch (empty notes folder), these are instantiated as real notes via `StorageService`. If the `SampleNotes` folder is missing (e.g. exe copied out on its own), sample creation is silently skipped rather than failing startup.

**Files dropped on a note are written as Markdown images.** A drop or paste of any file copies it into the note's `assets` (`ImageAssetImport.CopyIntoAssets`) and inserts `![name](assets/name)`; holding Shift, and any folder, inserts `![name](<original path>)` instead and copies nothing. One syntax covers both because `MarkdownRenderer` hands every `![...](...)` to the view's `CreateMarkdownImage`, which renders a real image when `LinkDetector.IsRenderableImageTarget` says so and otherwise builds a file chip (`.FileChips.cs`) — so the parser never had to learn about attachments. `ImageAssetImport.BuildFileMarkdown` wraps targets containing spaces or parentheses in `<...>`, which `MarkdownRenderer` already passes through verbatim. The chip is an `InlineUIContainer` carrying a `FileChipTarget` in its `Tag`; `ContentBox_PreviewMouseDown` (`.EditMode.cs`) walks up from the click to find it and opens it on a **single** click, like a hyperlink. Double-click is what enters edit mode, and that tunnelling handler runs before anything the chip could handle itself, so a double-click chip would start editing instead of opening; the second button-down on a chip is swallowed for the same reason. Executable extensions confirm before opening. Right-clicking a chip adds **Open** and **Open with...** at the top of the body menu, captured on right-button-down like the image items (`ContextMenuOpening` only reports the menu's owner). **Open with...** runs `rundll32 shell32.dll,OpenAs_RunDLL <path>` rather than ShellExecute's `openas` verb, which fails with ERROR_NO_ASSOCIATION (1155) unless that verb is registered for the extension (`.txt` did not have it); the path is passed unquoted because that entry point reads the rest of the command line. Icons come from `FileIcons` (`SHGetFileInfo`, cached per extension except for `.exe`/`.lnk`-style per-file icons, `DestroyIcon` after each read, `Freeze`d sources) — no thumbnails, and `SHGFI_USEFILEATTRIBUTES` keeps a missing or slow network file from blocking the render. `IsImageOnlyContent` checks the target really is an image, or a note holding one chip would lose its padding.

**draw.io diagrams are ordinary PNGs that happen to be editable.** draw.io hides the diagram XML in a PNG text chunk, so such a file is both a picture the note renders and a drawing draw.io can reopen. `DrawioFiles.IsDiagram` decides by content, not extension: it walks the PNG chunks for a `tEXt`/`zTXt`/`iTXt` keyword of `mxfile` or `mxGraphModel`, stopping at `IDAT` (draw.io writes it before the pixels), and takes `.drawio`/`.dio`-style names on trust. That gates an **Edit in draw.io** item at the top of the image menu and of a file chip's menu; `DrawioFiles.FindExecutable` uses `AppSettings.DrawioPath` when set and otherwise looks in the usual install folders. After launching draw.io, `.Drawio.cs` keeps an `ExternalFileMonitor` on that file until the note closes, so each save redraws the note (the same monitor the external-file notes use, which is what notices a save while draw.io holds the file open). Reloading only works because `GetOrLoadNormalizedImage` passes `BitmapCreateOptions.IgnoreImageCache`: WPF keeps its own per-URI decode cache and otherwise hands back the old pixels no matter how often the file is re-read.

## Conventions

- Write git commit messages in English; chat with the user stays in whatever language they use.

## Note management and reminders

- `NoteLayers` orders `StickyNote.LayerOrder` within the always-on-top and normal bands. Smaller ranks are in front. `App.ApplyLayerOrder` restores this order without activation. By default it only reorders notes among themselves (per topmost band, chaining each note below the previous with `PlaceBelow`, the last touched note first) so automatic reorders never lift notes over other apps — opening the tray menu makes the app foreground, where raising every note with `HWND_TOP` would do exactly that. `bringToFront: true` (Show all, showing a hidden note, note-list layer moves) raises every note; reminder editors defer it until closing. List sorting must never write layer ranks. Layer moves operate on the full, unfiltered layer view and preserve selection order.
- `NoteManagerWindow` uses clickable column headers, case-insensitive plain/wildcard/regex search, and a 30-entry persisted search history. Regex matching has a timeout. History stores valid queries when committed or when the input loses focus.
- `GlobalNoteHotkey` registers Ctrl+Alt+N by default using a message-only HWND and `MOD_NOREPEAT`. A replacement is registered before the previous binding is released, preserving the old binding on conflict. Dispose the registration on exit. The settings editor requires Apply; other settings remain immediate.
- `AppSettings.ClipboardNoteHotkey` (default Ctrl+Alt+Shift+N — Ctrl+Alt+V would take Office's Paste Special) registers a second `GlobalNoteHotkey` for `App.AddNewNoteFromClipboard`, which the tray menu also offers. `StickyNoteWindow.TryBuildClipboardNoteContent` builds the body before any window exists: image files, then text, then bitmap (Office puts a picture of the selection next to its text), saving images into the new note's `assets`. The note opens in view mode via `RevealNewNote`.
- `AppSettings.StartHidden` opens note windows without showing them (`OpenNoteWindow(note, show: false)`). It never writes `StickyNote.IsHidden`, so Show all brings the notes back as usual.
- External notes are refreshed by `ExternalFileMonitor`: a FileSystemWatcher plus polling of the file's length (read through an opened handle — NTFS directory entries lag while a writer keeps the file open, and the watcher stays silent) and last-write time. All notes share one `ExternalFilePoller` timer that checks every `ExternalFile.PollIntervalMs`. A note joins it when opened, on a watcher event, on hover and on activation, and leaves after `PollStopAfterMs` without a change (the watcher stays); the timer stops when no note is left. Before a note leaves, `FileHolders.Query` asks Windows which processes hold the file open (`NtQueryInformationFile` / `FileProcessIdsUsingFileInformation`, ignoring this process's own handles). While another process holds it — the very case the watcher misses — polling never stops (`AppSettings.ExternalFile.PollWhileWriterHoldsOpen`, default true). The query needs a handle, but opens it with `CreateFileW` and `FILE_READ_ATTRIBUTES` only: such a handle takes no part in share-mode arbitration, so a writer that reopens the file exclusively (`FileShare.None`) is never blocked by it, and a file already held that way can still be asked about. Opening for `FileAccess.Read` instead would block that writer — measured at 95 failed opens in 3s of probing, which `Holders_DoesNotGetInTheWayOfAWriterThatOpensExclusively` guards. The query costs ~25ms, so it runs only at the stop decision, at most once per `PollStopAfterMs` per note, never on the poller's lock. Note that directory-entry lag (`FileInfo.Length` vs the handle's length) is *not* a usable signal for this — on current Windows the metadata stays in sync while a writer appends. The poller raises `Polled` / `PollingStopped` (worker threads); the window fades the `ExternalPollingIndicator` dot on each check and sets `StickyNoteViewModel.IsExternalPolling`. The dot's space is reserved on every external note (`TitleTextMargin`) so the title never shifts. Callbacks arrive on worker threads; `ReloadExternalContent` marshals to the UI thread and applies the existing throttle.
- `DiagnosticTrace` writes `logs\trace.log` only when `AppSettings.EnableDiagnosticTrace` (JSON-only) or `SCREENPINNOTES_TRACE=1` is set. `StickyNoteWindow.Diagnostics.cs` logs sizing/activation/mouse Windows messages, `SizeChanged`, fold transitions (with the calling frames) and the environment (drag-full-windows, remote session, double-click metrics) so environment-specific resize/fold bugs can be diagnosed from a user's PC. Guard call sites with `DiagnosticTrace.Enabled` so messages are not built when off, and never log note titles or content.
- `AddNewNote` calls `StartEditingNewNote` after creating the window. Existing notes loaded from disk and external-file notes retain their normal viewing behavior.
- `ReminderDialog` uses a DatePicker and explicit time input. Offset buttons add to the entered datetime; reset reads the current clock on click. Windows notifications, alert windows, and `FlashNote` are independent methods; at least one must be selected.
- Note positions are logical pixels relative to the scale of the monitor they were saved on, so `StickyNote` also records `PositionScale` (that scale; 0 = unrecorded) and `PositionLayout` (the monitor layout signature from `MonitorLayout`; empty = unrecorded, adopted on the next position write). `MonitorLayout` re-reads the monitors from the OS on every call and works in physical pixels — WinForms `Screen` caches, and its list can be stale at the exact moment Windows relocates windows off a removed monitor, which is when a wrong answer would persist a temporary position as the note's own. `StickyNoteWindow.ReconcileScreenPlacement` (`.Monitors.cs`) runs at `OnSourceInitialized`, on re-show, and from `App`'s debounced `DisplaySettingsChanged`: it moves the note back to its saved position — in physical pixels when `PositionScale` is recorded, otherwise by assigning `Left`/`Top` and letting WPF resolve them (it places the window at the system scale, then re-reads the position at the destination monitor's scale, which lands correctly in most layouts; imposing the primary scale there would move notes saved before this feature) — then nudges it onto a monitor that can show it if its title bar would not be grabbable there. While `PositionLayout` differs from the current layout, `NoteGeometryState` drops position writes (sizes are still stored), so the rescued spot is never saved and the note returns home when the layout does. Dragging a note is the one gesture that adopts the current layout as its home (`AdoptCurrentLayoutAsHome`), so a permanently changed resolution does not leave notes unable to remember where they were rearranged. See `docs/note-state-and-persistence.md`.
- `FlashNote` defaults to true and reveals hidden notes on delivery. `App.RevealForReminder` shows only that note and, when `AppSettings.BringReminderNoteToFront` (default true; always for the alert window) is set, lifts just that note over other apps with `BringAboveOtherWindows` (a Topmost on/off toggle, which works even when the app is not foreground and takes no focus). External-file update flashes never raise the note. The overlay fills the whole note with translucent orange and pulses for ten seconds without changing saved opacity/content (an external-file update with `ERROR`/`FATAL` pulses a red border and, twice, animates `RootBorder`/`TitleBar` backgrounds from their bound colors to `ErrorTintColor` — 25% toward red — with discrete brush keyframes, so text stays uncovered and stopping the animation restores the bindings; ordinary updates pulse only the border; update flashes are skipped only while the note is the actual foreground window — `IsActive` alone stays true for a note activated while the app was in the background, e.g. at startup), stopping on interaction or hiding. Keep this separate from the note's theme brushes and persisted appearance.
- A folded note shown in the taskbar opens when the user picks it there, with Alt+Tab or in Task View (`HandleTaskbarMessage` in `.Taskbar.cs`), but not when Windows merely hands it the focus after another window closes or minimizes. Cross-process `WM_ACTIVATE` carries no previous window (`lParam` is 0) and Alt is already up when Alt+Tab commits, so `ShellSwitchTracker` records foreground changes with a WinEvent hook and treats the activation as a user switch only if the previous foreground window was a shell switcher (taskbar within 1.5s, or a visible/just-closed switcher such as `XamlExplorerHostIslandWindow`/`ForegroundStaging`), or the cursor is over the taskbar.
